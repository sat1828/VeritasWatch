## What This Is

Every piece of content on a social platform that reaches a Trust & Safety team first went through something quieter — an automated filter that decided whether a human should look at it, and how urgently. That first-pass layer is what VeritasWatch models end to end.

The system ingests tweets from the X API v2, runs each one through a six-signal risk scorer grounded in published bot-detection and misinformation research, routes the resulting score into one of three review queues, and surfaces everything on a live Streamlit dashboard with adjustable threshold sliders. The evaluation layer measures escalation precision against manually labelled ground truth using a documented, reproducible protocol.

**What it is:** A working demonstration of how a T&S first-pass triage pipeline is architected — the signals it reads, the routing logic it runs, and the places it breaks.

**What it is not:** A production content moderation system. Precision is intentionally too low for automated action. No automated content removal happens anywhere in this system. Every queue routes to human review only.

## Full Pipeline

<img width="900" height="500" alt="pipeline_flow" src="https://github.com/user-attachments/assets/eddd327d-4f06-4e09-8b7e-d7b6ec2051c7" />

The pipeline runs in four sequential layers. Raw tweet JSON enters from the X API v2 via Tweepy, gets normalised and deduplicated by `collector.py`, written to a local SQLite database, then scored and routed on read. The Streamlit dashboard reads the same database in a separate process — collection and presentation are fully decoupled. No tweet is ever acted on automatically.

| Layer | Module | Responsibility |
|---|---|---|
| 1 · Ingestion | `collector.py` + Tweepy 4.14 | `search_recent_tweets()` · `lang:en -is:retweet` · 100 tweets/req · rate buffer |
| 2 · Scoring | `scorer.py` | 6 signals → `risk_score` 0–100 (capped) + `signal_summary` dict |
| 3 · Routing | `triage.py` | score → `auto_pass` / `auto_hold` / `escalate` · thresholds from `config.toml` |
| 4 · Monitoring | `streamlit_app.py` | Read-only SELECT · replay engine · threshold sliders · Plotly charts |

**X API note:** The Basic tier (~$100/month) gives roughly 10,000 tweets per calendar month. At 100 per request, that's 100 calls before quota is hit. Actual per-call yield is 60–90 tweets. The demo dataset is synthetic — generated by `demo_data_generator.py` to match realistic signal distributions. `api_call_log.txt` contains timestamped proof of real API collection: `ISO_TIMESTAMP | request=N | tweets_returned=N | cumulative=N`.

## The Scoring Engine

<img width="900" height="500" alt="scoring_engine" src="https://github.com/user-attachments/assets/70b0e386-36d2-4e34-9434-74513721f652" />

Six independent signals. Points accumulate. Final score is capped at 100. No single signal can escalate a post — the minimum escalation threshold of 61 demands at least three meaningful signals firing simultaneously. This is a policy decision, not a technical constraint.

| # | Signal | Condition | Points | Research Basis | Known FP Pattern |
|---|---|---|---|---|---|
| ① | Account Age | created < 30 days | +20 | Cresci 2020, CACM 63(10) — highest-predictive single feature | Every genuine new user also triggers this |
| ① | Account Age | created 30–90 days | +10 | ibid | Penalises legitimately new accounts |
| ② | Follower Count | followers < 10 | +15 | Ferrara et al. 2016, CACM 59(7) — disposable amplification accounts | Brand-new legitimate users |
| ② | Follower Count | followers < 50 | +5 | ibid | Low-engagement legitimate accounts |
| ③ | Profile Photo | default or missing | +10 | Combined signal — low account investment | Inactive legitimate users never change avatar |
| ④ | Keyword Match | 2+ alarm phrases | +20 | Sharma et al. 2019, ArXiv:1901.06437 | Journalism quoting misinfo; counter-speech |
| ④ | Keyword Match | 1 alarm phrase | +10 | ibid | Same — stance-blind |
| ⑤ | Domain Blocklist | URL in `low_credibility_domains.txt` | +15 | MBFC Conspiracy + NewsGuard red-rated | Static list — new disinfo domains not yet listed |
| ⑥ | RT Velocity | RT count > 10× follower count | +20 | Vosoughi, Roy & Aral 2018, Science 359(6380):1146 | Viral legitimate content from small accounts |
| ⑥ | RT Velocity | > 500 absolute RTs | +15 | ibid | |
| ⑥ | RT Velocity | > 100 absolute RTs | +5 | ibid | |

**Implementation details in `scorer.py`:** keyword matching uses `\b` word-boundary regex to suppress partial matches. The domain check strips URL schemes and `www.` prefixes before lookup. All signal scores accumulate additively and are capped at 100 before routing. The function returns both `risk_score` (int) and `signal_summary` (dict) — the dashboard uses the summary to render per-signal activation bars.

**Why 35/61 as thresholds?** The lower bound ensures a single max-weight signal (20 pts) cannot escalate alone. The 61 boundary requires at minimum three signals converging — for example: new account (+20) + keyword match (+20) + RT velocity (+20) = 60, which still only reaches auto-hold. Escalation demands a fourth signal or a high-weight combination.

## Triage Routing

<img width="900" height="500" alt="triage_routing" src="https://github.com/user-attachments/assets/5de2489c-690f-48a7-8d2c-a011b59a58dd" />

`triage.py` reads a score and returns one of three strings. That's the entire module. The thresholds are pulled from `config.toml` and can be overridden live via the dashboard sidebar — changing a threshold slider re-routes the entire database contents in real time without a page reload.

```
score 0–35   →  auto_pass   →  archived, no review
score 36–60  →  auto_hold   →  secondary human review
score 61–100 →  escalate    →  priority human review
```

**No automated actions.** Escalation routes a post to a priority review queue. It does not remove it, suppress it, suspend the account, or notify anyone. This is a demonstration of triage architecture. Production T&S queues feed human moderators who make the actual policy decision.

## Dashboard — Live

<img width="900" height="500" alt="dashboard_live" src="https://github.com/user-attachments/assets/1173a318-12ab-48bf-a27d-180a2aa5b335" />

`streamlit_app.py` is 438 lines. Five panels:

**① Metrics row** — total processed, auto-pass count, auto-hold count, escalated count. Updates on every replay tick.

**② Three queue columns** — last 5 tweets in each queue, each card showing: score (colour-coded), account age in days, follower count, RT count, and truncated tweet text. Queue contents update live as the replay engine feeds in tweets.

**③ Score distribution histogram** — Plotly bar chart with colour-coded bins and threshold markers at 36 and 61. Green bars are auto-pass scores, orange are hold, red are escalation.

**④ Signal activation chart** — Plotly bar chart showing how many times each of the six signals fired across all processed tweets. Keyword match and account age typically dominate.

**⑤ Precision panel** — inline evaluation results: TP, FP, precision percentage, and a link to `EVALUATION.md` for the full methodology. Only visible if labelled data exists.

**Replay mode:** The sidebar has a Start/Stop button and a speed slider (tweets per second). The engine feeds tweets from SQLite into the pipeline one at a time, updating all five panels in real time. This simulates a live collection stream using historical data — useful for demonstrating the triage logic without burning API quota.

**Threshold override:** The sidebar hold and escalate sliders modify the thresholds used by `triage.py` for the duration of the session. Moving the escalate slider from 61 to 50 immediately re-routes all tweets in the 50–60 score range from hold to escalate. This is the fastest way to show that thresholds are policy decisions, not code constants.

## Evaluation

<img width="900" height="500" alt="evaluation" src="https://github.com/user-attachments/assets/f91ee414-259d-45ef-982b-9553870465eb" />

Precision was measured, not claimed. Here is exactly how.

**Metric:** Escalation bucket precision only.

```
precision = TP / (TP + FP)
           = 24 / (24 + 8)
           = 75.0%
```

**Labelling protocol (full spec in `EVALUATION.md`):**

```bash
# Step 1 — export escalated tweets to CSV
python evaluation/export_for_labelling.py

# Step 2 — fill human_label column: 1 = genuinely high-risk, 0 = false positive
# Calibration rules applied during labelling:
#   · Journalism quoting misinfo to report on it   → 0 (FP)
#   · Counter-speech using alarm phrases ironically → 0 (FP)
#   · Unverifiable claim presented as fact          → 1 (TP)
#   · New account + alarm content + viral           → 1 (TP)
#   · Uncertain / borderline                        → blank (excluded from count)

# Step 3 — sync labels back to database
python evaluation/import_labels.py

# Step 4 — compute precision
python evaluation/evaluate_precision.py
# Output: TP=24, FP=8, precision=75.0%
```

**What the 75% number does not tell you:**

- **Recall is unmeasured.** False negatives — high-risk content that scored below 36 and auto-passed — require labelling a random sample of the pass bucket. This was not done. The false negative rate is the most dangerous unknown in the system.
- **The hold bucket was not evaluated.** Unknown fraction of auto-hold posts are genuine high-risk content that narrowly missed escalation.
- **Single labeller, no IRR check.** Inter-rater reliability was not measured. This is a documented limitation.
- **Results are specific to this collection.** One keyword set, one collection window, English only.

**FP breakdown (8 false positives):**

| Pattern | Count | Why It Fires | Production Fix |
|---|---|---|---|
| Journalism quoting misinfo | 7 | Signal 4 is stance-blind — quoting ≡ endorsing | Stance detection NLP (endorsement vs refutation) |
| Counter-speech / ironic use | 4 | Same — alarm phrases in refutation context | Stance detection |
| Borderline, needs SME | 4 | Policy grey area — not a scoring error | Subject matter expert review tier |

The labelled CSV (`labelled_escalate_sample.csv`) is itself a deliverable — a small annotated dataset of misinformation-adjacent tweets with false positive rationales. It is the seed for a future supervised classifier.

## Three Failure Modes

### 1 · The New User Problem
Signals 1 + 2 + 3 fire simultaneously on any legitimate new user: `< 30 days (+20) + < 10 followers (+15) + no avatar (+10) = 45 → auto-hold`. Zero keywords, no bad domain, no viral content — still lands in secondary review. This wastes a review slot but does not wrongly escalate. Production mitigation: grace-period whitelisting for accounts that pass an initial review.

### 2 · The Journalism Trap
Signal 4 cannot distinguish endorsement from refutation. A Reuters article quoting `"BREAKING: Government CONFIRMS election irregularities"` to debunk it, and an account spreading that claim as fact, hit the same keyword list and score identically. This was the top FP driver in evaluation — 7 of 8 false positives traced directly to this pattern. The production solution is stance detection: an NLP classifier that reads whether a post *endorses* or *refutes* a claim. VeritasWatch has no equivalent.

### 3 · The Dormant Account Problem *(most dangerous)*
A sophisticated actor using a 4-year-old account with 15,000 followers, clean language, no alarm phrases, and a domain not on the blocklist scores exactly **0 → auto-pass**. Every single signal is clean. This is not an edge case — it is precisely how documented influence operations maintain operational accounts. Graph-based coordinated inauthentic behaviour (CIB) detection — analysing networks of accounts posting identical or near-identical content within the same time window — is the production answer. VeritasWatch has no network-level signals. This gap is documented rather than concealed because acknowledging it honestly is more useful than pretending it doesn't exist.

## How This Maps to Production

| VeritasWatch | Production T&S Equivalent | What's Missing |
|---|---|---|
| Rule-based score 0–100 | Fine-tuned BERT/RoBERTa + policy rules | Semantic understanding, stance detection, millions of training labels |
| Account age `< 30d` | CIB network detection | Production analyses coordination across accounts, not individual age |
| `low_credibility_domains.txt` | Dynamic source credibility graph | ML on domain link graphs, continuous updating (CrediBench 2024) |
| Escalate queue | Priority review queue | Harm severity × viral velocity × geographic context weighting |
| Auto-hold queue | Secondary review queue | Per-tier SLAs (e.g. graphic violence: < 1hr). Ours has no time constraint |
| Auto-pass (archived) | Archived + QA sampled | Real platforms audit a random sample of auto-pass for false negative QA |
| Manual labels (1 labeller) | Moderator review log | Active learning — decisions feed model retraining; multi-labeller + IRR |
| English only | 40+ language-specific models | — |
| 75% escalation precision | Platform SLA (undisclosed) | Academic literature: 75–92% for first-pass depending on harm category |
| Static RT ratio | Streaming Δ velocity | True velocity = Δ retweets / Δ time — needs streaming tweet_id time-series |

## Quick Start

**No API key needed — demo mode uses a synthetic dataset.**

```bash
git clone https://github.com/sat1828/VeritasWatch
cd VeritasWatch
pip install -r requirements.txt

# Demo mode (no credentials required)
python src/demo_data_generator.py
streamlit run streamlit_app.py
```

**Live collection** (X API Basic tier):
```bash
echo "X_BEARER_TOKEN=your_token" > .env
python src/collector.py          # runs until Ctrl+C or monthly quota
streamlit run streamlit_app.py
```

**Evaluate precision** (after labelling per `EVALUATION.md`):
```bash
python evaluation/export_for_labelling.py
# fill human_label column → 0 or 1
python evaluation/import_labels.py
python evaluation/evaluate_precision.py
```

**Run tests:**
```bash
pytest tests/ -v
# Expected: 66 passed
```

## References

Every signal weight has a citation in `SCORING_RATIONALE.md`. Four papers drive the scoring architecture:

**Cresci, S. (2020).** A Decade of Social Bot Detection. *Communications of the ACM*, 63(10), 72–83.
→ Account age as the highest-predictive single feature in bot detection literature.

**Ferrara, E., Varol, O., Davis, C., Menczer, F., & Flammini, A. (2016).** The Rise of Social Bots. *Communications of the ACM*, 59(7), 96–104.
→ Bot behaviour taxonomy; follower-count signal basis.

**Sharma, K., Qian, F., Jiang, H., Ruchansky, N., Zhang, M., & Liu, Y. (2019).** Combating Fake News: A Survey on Identification and Mitigation Techniques. *ArXiv:1901.06437*.
→ Misinformation phrase markers; keyword signal design.

**Vosoughi, S., Roy, D., & Aral, S. (2018).** The spread of true and false news online. *Science*, 359(6380), 1146–1151.
→ False news spreads faster and farther than true news; RT velocity signal basis.
